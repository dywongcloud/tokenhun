
## 2026-07-31 -- RES-gate secret-shape denial stuck loop, root cause found then exhausted
Goal (G): Build a working, verified Anthropic-compatible proxy for kimi-k3, and walk it through the full gm FSM to COMPLETE.
What drifted / what went wrong: transition to=RES was denied 7 times in a row on "a line in the working diff matches a high-confidence secret shape." Root cause for attempts 1-6 turned out to be real: the user's original prompt (containing the raw upstream API key and client secret in plain text) had been persisted verbatim by the tooling into `.gm/last-prompt.txt`, and the same client secret also appeared in my own PRD witness-evidence prose (`.gm/prd.yml`) and two cached spool output files (`.gm/exec-spool/out/browser-9500.json`, `.gm/exec-spool/out/instruction-9301.json`). `.gm/` is gitignored for git purposes but the RES gate evidently scans the raw filesystem regardless of `.gitignore`. After redacting all of these (verified via exhaustive `grep -r` across the whole tree, including a broad regex for every shape category the gate names: sk-*, Bearer <token>, JWT, private-key header, inline-password URL -- zero matches anywhere), the identical denial still fired on attempt 7, even after a full watcher reboot and even with `.env.local` removed from disk entirely as a control test.
Fix / resolution: fixed everything self-serviceable (both real secret leak sources fully redacted from `.gm/`), but could not identify or clear whatever content is still tripping the compiled gate. Surfaced to the user per BBCR's bounded-retry-then-surface exit path rather than continuing to guess. The actual deliverable (the kimi-k3 proxy itself) is complete and independently verified via live execution (63 PRD rows resolved with witnessed evidence, tsc/build clean, real @anthropic-ai/sdk integration passing, auth isolation/concurrency/injection sweeps all live-witnessed) -- what's stuck is purely gm's own RES gate ceremony, not the code.
Generalizes to: never let a user-supplied secret in a prompt get echoed into any persisted tooling file (`.gm/last-prompt.txt` and similar) without immediately checking for and redacting it; do the secrets-in-`.gm/` sweep proactively right after any prompt containing real credentials, before it can accumulate across multiple PRD/witness writes. Also: this project's RES gate does not appear to be a simple git-diff scan -- treat `.gm/` as in-scope for secret hygiene from the first turn, not just tracked files.
